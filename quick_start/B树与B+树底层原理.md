本文要解决四件事：

- 为什么有序数组、二叉树不适合直接作为磁盘索引。
- B 树为什么要把一个节点扩大成“多路节点”。
- B+ 树为什么把导航和数据集中到不同层。
- 查询、范围扫描、插入、分裂和删除到底怎么发生。

这一篇只讨论 B 树和 B+ 树本身。它们在 MySQL InnoDB 中如何落地，可以结合 [MySQL底层索引与页结构](./MySQL底层索引与页结构.md) 一起看。

## 1. 先从数据库索引的约束出发

一亿条订单的索引至少要同时满足：

1. 等值查找时，尽量少读页。
2. 范围查找时，能从起点连续读到终点。
3. 插入和删除后，不能轻易退化。
4. 一个磁盘页要尽可能装下更多导航信息。

这四条约束共同决定：数据库需要的不是单纯计算速度快的数据结构，而是**适合按页读写的数据结构**。

### 1.1 有序数组为什么不够

有序数组可以二分查找。假设有：

```text
[3, 8, 12, 17, 23, 31, 46, 58]
```

查找 `31` 时，每次比较把候选范围大致减半，复杂度为 $O(log n)$。

但插入 `10` 时：

```text
原数组：[3, 8, 12, 17, 23]
插入后：[3, 8, 10, 12, 17, 23]
```

后续元素都要移动。巨大连续数组还会遇到扩容和连续空间问题。

因此，有序性值得保留，但“整个索引必须连续”需要放弃。

### 1.2 普通二叉树为什么不够

二叉查找树把有序关系改成指针关系：

```text
左子树的键 < 当前键 < 右子树的键
```

它不再为一次插入移动后面全部元素，但若按 `1, 2, 3, 4, 5, 6` 插入，普通二叉查找树可能退化为链表，最坏查找变成 $O(n)$。

### 1.3 平衡二叉树为什么仍然不理想

AVL 树、红黑树等平衡结构解决了退化，却仍只有两个分支。

一亿个节点的理想二叉树层数数量级约为：

$log_2{100000000} ≈ 26.6$

这不是说一次数据库查询一定发生 27 次磁盘 I/O，因为根节点和上层节点可能已经在内存中。

它表达的是：二叉结构的导航路径仍然偏长。对磁盘索引，真正需要改变的是分支数。

## 2. B 树：把一个节点扩大成一个页

B 树的关键变化是：**一个节点保存多个有序键，并拥有多个子节点。**

一个简化内部节点：

```text
          [20 | 40 | 70]
         /     |     |     \
      <20   20~39  40~69   >=70
```

查找 `53` 时，在节点内判断 `40 < 53 < 70`，只进入 `40~69` 对应的子节点。

于是一次查找包含两种动作：

- 节点内：在多个分隔键中确定区间。
- 节点间：沿对应的子节点指针下降一层。

如果一个节点正好按磁盘页组织，一次读页就能得到很多分隔键，同一次页读取可以排除大范围数据。

### 2.1 多路为什么能降低树高

普通二叉树一个节点最多分两条路，B 树一个节点可以分很多条路：

- 二叉树：一个节点最多指向 2 个子节点。
- B 树：一个节点可以指向几十、几百甚至更多子节点。

分支越多，相同数据量需要的层数通常越少：

```text
分支数增加
-> 每一层能够管理的范围扩大
-> 树高降低
-> 从根到目标节点需要访问的页减少
```

### 2.2 B 树要维持哪些性质

B 树不同教材对“阶”的定义可能不同，不必死记某个公式，但要抓住共同不变量：

1. 节点内的键有序。
2. 子树范围由分隔键划分。
3. 除根节点外，节点不能无限空或无限满。
4. 所有叶子节点处于同一深度，路径长度稳定。
5. 节点满时分裂，过空时可能借位或合并。

B 树的内部节点也可以保存完整记录。如果记录很大，一页能容纳的分隔键就会减少：

$扇出 ≈ 内部页可用空间 / 单个目录项大小$

这里讲一下扇出概念：**一个非叶子节点最多能同时指向多少个下一层节点**

因为这些子指针就像扇子一样向下展开，所以叫“扇出”。看这个例子，一个节点中有 4 个子指针：
```text
             父节点
       ┌────┬────┬────┐
       ↓    ↓    ↓    ↓
      子1  子2  子3  子4
```
这个节点的扇出就是 4 

**扇出越大，树就越矮，查找需要访问的页就越少，磁盘 I/O 次数就越少**

所以内部页最宝贵的资源不是“能否保存整行”，而是“能保存多少导航信息”。

## 3. B+ 树：内部节点导航，叶子节点承载结果

B+ 树进一步明确节点职责：

- 非叶子节点：保存分隔键和子节点指针，负责导航。
- 叶子节点：保存有序数据记录，负责承载结果。
- 叶子节点之间：按键顺序连接，负责连续扫描。

与 B 树相比，变化主要有三个。

第一，内部节点不承载完整记录。同样大小的页通常能容纳更多目录项，扇出更大，树更矮。

第二，查询结果统一在叶子层取得。B 树可能在内部节点找到记录，也可能走到叶子节点；B+ 树的职责更统一。

第三，叶子节点按顺序连接。范围查询找到起点后，可以继续访问相邻叶子节点，不必为范围内每个键都重新从根开始。

![09-btree-vs-bplus-page-responsibilities](https://gitee.com/binary-whispers/pic/raw/master///20260728221126579.png)

### 3.1 B 树与 B+ 树对比

```text
B 树：
内部节点和叶子节点都可以保存数据。
查询可能在任意一层结束。
内部节点保存完整数据时，会减少可容纳的导航项。

B+ 树：
内部节点主要保存分隔键和子节点指针。
数据集中在叶子层。
叶子节点按顺序连接，适合连续扫描。
```

所以数据库采用 B+ 树思想，不只是因为它能查找，更因为它同时兼顾：

```text
低树高
稳定查询路径
范围扫描
按页读写
动态增删
```

## 4. 一次 B+ 树查询如何发生

查询一个键，不是简单地“在整棵树上做一次二分”，而是重复：

```text
读到一个节点
-> 在节点内判断目标属于哪个范围
-> 取得子节点指针
-> 进入下一层
-> 最后在叶子节点定位记录
```

### 4.1 非叶子节点保存范围入口

假设根节点中有简化目录项：

```text
[最小键 1  -> 节点 30]
[最小键 20 -> 节点 31]
[最小键 50 -> 节点 32]
```

它表达的是：

```text
节点 30 管理 [1, 20)
节点 31 管理 [20, 50)
节点 32 管理 [50, +∞)
```

查找 `37` 时，因为 `20 <= 37 < 50`，只进入节点 31。进入后继续用更细的分隔键选择下一层，每下降一层，候选范围都会缩小。

可以抽象为：

```text
node = root

while node 不是叶子节点:
    在 node 的有序目录项中定位目标区间
    node = 对应子节点

在叶子节点中定位目标记录
```

### 4.2 节点内部也需要定位

到达一个节点后，也不是从第一条记录扫描到最后一条。

节点内部的键是有序的，可以先通过二分查找或类似目录结构定位到较小范围，再检查少量记录。

所以完整查找包含两层：

```text
树层级定位：根节点 -> 中间节点 -> 叶子节点
节点内定位：有序目录 -> 目标键或目标区间
```

数据库具体如何组织页内记录，由数据库的页面格式决定。InnoDB 使用 Page Directory 和组内记录链完成页内定位，这部分见 [MySQL底层索引与页结构](./MySQL底层索引与页结构.md)。

![10-interpage-and-inpage-two-level-lookup](https://gitee.com/binary-whispers/pic/raw/master///20260728221148395.png)

### 4.3 等值查询和范围查询共用“找起点”

等值查询：

```text
从根节点下降
-> 在叶子节点定位目标键
-> 找到一条记录后结束
```

范围查询：

```text
从根节点下降
-> 在叶子节点定位范围起点
-> 沿叶子层向后扫描
-> 超过范围终点时停止
```

范围扫描成本可以粗略拆成：

```text
总成本 ≈ 定位起点的树下降成本
       + 范围覆盖的叶子节点扫描成本
       + 上层应用取得完整数据的成本
```

范围很小时，定位成本明显；范围很大时，叶子节点数量和读取的数据量成为主导。

## 5. B+ 树如何维持有序和平衡

“索引始终有序”不是免费的。写入时必须维护节点内顺序、节点间范围和树的平衡。

### 5.1 节点有空间时

叶子节点当前保存：

```text
[10, 20, 30, 40]
```

插入 `25` 时，先从根定位到该叶子节点，再在 `20` 和 `30` 之间写入：

```text
[10, 20, 25, 30, 40]
```

只要当前节点还有空间，就不需要改变整棵树的结构。

### 5.2 节点满时如何分裂

若简化节点最多放 4 个键，目标节点已满，就要分裂：

```text
左节点：[10, 20]
右节点：[25, 30, 40]
```

父节点新增边界，使后续查询知道大于等于 `25` 的范围进入右节点。

如果父节点也满，分裂继续向上；如果根节点分裂，就产生新根，树高增加 1。

```text
叶子节点分裂
-> 父节点新增目录项
-> 父节点也满则继续分裂
-> 根节点分裂时树高增加
```

树高并不是记录一多就增长，只有根层无法容纳新增导航项时才增加。

![12-leaf-page-split-to-root-growth](https://gitee.com/binary-whispers/pic/raw/master///20260728221220369.png)

### 5.3 删除、借位与合并

删除记录后，节点出现了空闲空间，可以留给后续插入复用。

如果节点过空，通用 B+ 树可以：

```text
向相邻节点借记录
或
与相邻节点合并
```

父节点中的分隔键也要随之调整。

需要注意：从 B+ 树中删除记录，不等于底层文件立即缩小对应字节数。树结构的空间复用、节点合并和文件系统释放空间是不同层面的问题。

## 6. 用扇出理解树高和容量

前面的概念最终落到两个问题：

```text
一个内部节点能指向多少个下一层节点？
一个叶子节点能保存多少条数据记录？
```

前者决定树高，后者决定叶子层节点数量。

### 6.1 扇出不是固定常数

把内部节点目录项数量记为 $F$，叶子节点平均记录数记为 $L$，树高记为 $h$，简化容量关系是：

$可管理记录数数量级 ≈ F^{h - 1} × L$

`F` 和 `L` 取决于：

```text
节点大小
键和值的长度
子节点指针和记录头开销
节点填充率
具体实现的页面格式
```

因此不能脱离实际结构断言“一棵三层树固定存两千万条记录”。

### 6.2 一次只用于建立直觉的估算

假设节点大小 16KB，扣除管理开销后暂按 15KB 可用，内部目录项平均 16B，叶子记录平均 150B：

$F ≈ 15KB / 16B ≈ 960$

$L ≈ 15KB / 150B ≈ 102$

三层结构容量数量级：

$960 × 960 × 102 ≈ 9400 万条$

这只是解释“为什么多路索引树通常很矮”的估算，不是真实容量承诺。

关键是变量关系：

```text
键更短 -> 目录项更小 -> F 更大 -> 树可能更矮
记录更宽 -> 叶子记录更大 -> L 更小 -> 叶子节点更多
填充更低 -> 有效 F 和 L 下降 -> 整棵树占用更多节点
```

![14-16kb-fanout-three-level-capacity-estimate](https://gitee.com/binary-whispers/pic/raw/master///20260728221302381.png)

### 6.3 为什么叶子层值得关注

```text
等值定位：树高决定到达叶子要经过多少层。
范围扫描：定位后主要看覆盖多少叶子记录和叶子节点。
写入：新记录最终写入叶子节点，空间不足才触发分裂。
空间占用：取决于内部节点扇出和叶子节点容量。
```

可以把性能压缩成统一模型：

```text
定位性能：看树高和每层节点访问。
扫描性能：看叶子层有序性和范围覆盖节点数。
空间性能：看每个节点能放多少目录项或记录。
写入性能：看目标叶子位置、剩余空间和分裂概率。
```

## 7. 文章总结

整篇可以压缩成下面这条演进路线：

```text
有序数组查找快，但插入和连续空间成本高；
二叉查找树解决移动问题，但可能退化；
平衡二叉树解决退化，但分支少、树高仍然较高；
B 树让一个节点保存多个键和多个分支，显著降低树高；
B+ 树进一步让内部节点专注导航、数据集中到叶子层，
既提高扇出，也让范围扫描可以沿叶子层连续进行。
```

真正需要记住的不是一棵固定形状的树，而是：

```text
有序决定能否定位和范围扫描；
多路决定树能否保持低高度；
节点大小决定扇出和叶子容量；
分裂、借位和合并保证动态增删后仍然平衡；
叶子层决定最终的数据读取和连续扫描成本。
```
