# MySQL 索引总结与常见面试题

> 适用范围：MySQL 8.4、InnoDB、普通 B-tree 索引。  
> 使用方式：这不是第六篇新知识，而是本周五篇索引笔记的总复习入口。周日先顺着主线复述，再回答面试题，最后做 SQL 判断题。

---

## 1. 先用一条主线串起全部内容

索引这一周的内容，可以压缩成下面这条因果链：

```text
数据很多，逐行扫描成本高
-> 用有序索引缩小扫描范围
-> 磁盘按页读写，所以索引节点也按页组织
-> B 树用多路节点降低树高
-> B+ 树让非叶子节点负责导航、叶子层承载结果并保持有序
-> InnoDB 用聚簇索引组织整行数据，用二级索引保存索引列和主键
-> 查询可能经历主键直达、二级索引回表或者覆盖索引
-> 联合索引按列顺序排序，决定查询能形成怎样的连续扫描区间
-> 索引只是候选路径，优化器会根据统计信息和成本决定是否使用
-> 最终用 explain 和 explain analyze 验证，而不是只凭规则猜测
```

一句话总纲：

> **索引优化的核心，不是“有没有索引”，而是能否用较小的索引读取、较窄的扫描范围和较少的回表，取得查询真正需要的数据。**

## 2. 索引到底解决什么问题

没有可用索引时，MySQL 可能需要从第一行开始检查，直到扫描完整张表。

```sql
select *
from orders
where user_id = 1001;
```

给 `user_id` 建立索引后，MySQL 可以先在有序结构中定位 `1001` 所在范围，再读取对应记录。

因此，索引不是“不查数据”，而是：

```text
把全表找
变成
先定位起点，再读取候选范围
```

索引的收益主要来自：

- 减少需要检查的行和页。
- 快速完成等值查询和范围查询。
- 在条件合适时利用索引顺序完成排序或分组。
- 在覆盖索引场景中，直接从索引返回结果，减少回表。

索引的代价也必须同时记住：

- 占用磁盘和 Buffer Pool 空间。
- `insert`、`update`、`delete` 时需要维护索引。
- 索引记录过宽会降低单页容量。
- 索引过多会增加写入成本，也会增加优化器选择候选路径的工作。

所以，索引是一种典型的：

```text
用空间和写入成本
换取查询速度
```

## 3. 为什么数据库索引需要 B 树和 B+ 树

### 3.1 数据结构的演进

#### 有序数组

优点：

- 可以二分查找。
- 范围数据天然连续。

问题：

- 中间插入、删除可能移动大量元素。
- 大型连续数组的扩容和空间管理困难。

#### 普通二叉查找树

优点：

- 不再要求整个索引连续存放。
- 正常情况下可以逐层缩小范围。

问题：

- 按有序值插入时可能退化成链表。

#### 平衡二叉树

优点：

- 通过旋转等方式避免退化。

问题：

- 每个节点最多只有两个分支。
- 数据量很大时树仍然较高，磁盘页访问路径较长。

#### B 树

B 树让一个节点保存多个有序键，并拥有多个子节点：

```text
一个节点容纳更多导航信息
-> 一个节点可以管理更多子页
-> 扇出增大
-> 树高降低
-> 从根到目标节点需要访问的页减少
```

#### B+ 树

B+ 树进一步分离职责：

- 非叶子节点主要保存分隔键和子节点指针，负责导航。
- 数据或索引记录集中在叶子层。
- 叶子页按键顺序连接，适合从范围起点连续扫描。

因此 B+ 树同时适合：

```text
等值定位 + 范围扫描 + 按页读写 + 动态增删
```

### 3.2 为什么 B+ 树比二叉树更适合磁盘索引

面试回答不要只说“B+ 树查询复杂度低”，更完整的因果关系是：

1. 数据库以页为基本读写单位。
2. 一个 B+ 树非叶子页可以保存很多目录项。
3. 扇出大，同样数据量下树通常更矮。
4. 从根到叶子需要访问的页更少。
5. 叶子层有序连接，范围扫描找到起点后可以继续向后读取。

注意两个边界：

- 上层索引页可能已在 Buffer Pool 中，所以树高不等于每次查询真实磁盘 I/O 次数。
- 不能死记“千万数据固定三层”。树高还受页大小、键长度、记录宽度和页面填充率影响。

### 3.3 B 树和 B+ 树的主要区别

| 对比项 | B 树 | B+ 树 |
|---|---|---|
| 内部节点 | 可以保存数据 | 主要保存导航信息 |
| 查询结束位置 | 可能在任意层 | 结果统一到叶子层 |
| 单个内部页的扇出 | 完整数据会占用空间 | 通常能容纳更多目录项 |
| 范围扫描 | 连续扫描不够直接 | 找到起点后沿叶子层扫描 |
| 数据库索引适配性 | 能完成查找 | 更适合按页导航和范围查询 |

## 4. InnoDB 如何把 B-tree 落到页面上

### 4.1 存储层级

InnoDB 的空间组织可以先记成：

```text
表空间 -> 段 -> 区 -> 页 -> 记录
```

- 表空间：保存 InnoDB 数据的逻辑容器。
- 段：按用途管理一组页面，例如索引的叶子页和非叶子页。
- 区：一组连续页面，用于批量分配空间。
- 页：InnoDB 管理和读写数据的基本单位。
- 记录：页中保存的索引记录或行数据。

默认 `innodb_page_size` 是 16KB，但它是在实例初始化时确定的，并不是所有实例都永远固定为 16KB。

### 4.2 一次定位包含两层查找

```text
树间定位：根页 -> 中间页 -> 叶子页
页内定位：页目录 -> 记录组 -> 目标记录
```

到达目标页并不意味着已经找到目标记录。页内还有有序记录、页目录，以及用于组织记录边界的 `infimum`、`supremum`。

### 4.3 一次等值查询

```sql
select *
from orders
where id = 800000;
```

粗略路径：

```text
聚簇索引根页
-> 根据分隔键选择下一层
-> 到达叶子页
-> 通过页目录缩小页内范围
-> 找到 id = 800000 的整行数据
```

### 4.4 一次范围查询

```sql
select id, created_at
from orders
where created_at >= '2026-07-01 00:00:00'
  and created_at < '2026-08-01 00:00:00';
```

粗略路径：

```text
定位范围起点
-> 沿有序叶子层继续扫描
-> 超过范围终点后停止
```

范围查询成本可以理解为：

```text
总成本 ≈ 定位起点
       + 扫描范围内的索引记录和叶子页
       + 需要时发生的回表
```

## 5. 聚簇索引、二级索引、回表和覆盖索引

### 5.1 聚簇索引

每个 InnoDB 表都有一个聚簇索引，用来存储行数据。

选择顺序是：

1. 有显式 `primary key`：使用主键作为聚簇索引。
2. 没有主键：使用第一个所有列均为 `not null` 的 `unique` 索引。
3. 两者都没有：InnoDB 创建隐藏行 ID，并建立 `gen_clust_index`。

聚簇索引叶子记录保存整行数据：

```text
primary：主键 -> 整行数据
```

所以主键查询到达聚簇索引叶子页时，通常已经取得整行，不需要“再去另一份表数据中找一次”。

### 5.2 二级索引

聚簇索引之外的索引称为二级索引。InnoDB 二级索引记录包含：

```text
二级索引列 + 主键列
```

例如：

```sql
create index idx_user_id
on orders(user_id);
```

可以简化理解为：

```text
idx_user_id：user_id -> id
primary：id -> 整行数据
```

### 5.3 回表

```sql
select *
from orders
where user_id = 10;
```

查询需要二级索引中不存在的列时：

```text
idx_user_id 找到 user_id = 10
-> 取得主键 id
-> 使用 id 查询聚簇索引
-> 取得整行数据
```

从二级索引取得主键，再查询聚簇索引取得其他列，这个过程叫回表。

### 5.4 覆盖索引

```sql
select id, user_id
from orders
where user_id = 10;
```

`idx_user_id` 中已有 `user_id` 和主键 `id`，查询可以直接从二级索引返回结果，不需要回表。这种“查询需要的列都能从某个索引取得”的情况叫覆盖索引。

覆盖索引不是一种单独的数据结构，而是索引相对于某条查询形成的使用效果。

### 5.5 为什么 `select *` 容易放大回表成本

`select *` 通常要求整行数据，而普通二级索引只保存索引列和主键。

如果条件匹配很多行：

```text
扫描大量二级索引记录
-> 取得大量主键
-> 大量回表
```

此时即使 `key` 显示使用了二级索引，查询也不一定快。优化器甚至可能认为全表扫描更便宜。

## 6. 联合索引和最左前缀

### 6.1 联合索引不是多棵树

```sql
create index idx_user_status_created
on orders(user_id, status, created_at);
```

这是一棵按照下列顺序组织的索引：

```text
先按 user_id 排序
user_id 相同，再按 status 排序
user_id、status 都相同，再按 created_at 排序
```

因此可以使用的连续左前缀包括：

```text
(user_id)
(user_id, status)
(user_id, status, created_at)
```

### 6.2 最左前缀的本质

最左前缀不是背 SQL 书写顺序，而是判断：

> 查询条件能否从联合索引最左边开始，在索引的有序结构中形成连续、可定位的区间。

下面两条 SQL 对索引使用没有本质区别，优化器可以调整谓词处理顺序：

```sql
where user_id = 10
  and status = 'paid';
```

```sql
where status = 'paid'
  and user_id = 10;
```

真正重要的是索引定义中的列顺序，而不是 `where` 条件书写顺序。

### 6.3 跳过最左列

索引是 `(user_id, status, created_at)`：

```sql
where status = 'paid';
```

整棵索引先按 `user_id` 排序，`status = 'paid'` 分散在不同 `user_id` 分组中，通常无法直接形成一个连续的精确定位区间。

### 6.4 中间断开

```sql
where user_id = 10
  and created_at >= '2026-07-01';
```

可以先使用 `user_id = 10` 定位，但跳过 `status` 后，`created_at` 只在每个 `status` 分组内部有序，通常不能继续构造一个完整连续的更窄区间。

### 6.5 范围条件

安全的复习表述是：

```text
等值条件通常可以继续向右构造索引范围；
遇到非等值范围后，后续列通常不能继续缩小整个扫描区间。
```

例如：

```sql
where user_id = 10
  and status > 'paid'
  and created_at = '2026-07-01';
```

通常可以用 `user_id` 和 `status` 构造范围；`created_at` 仍可能参与扫描过程中的过滤，甚至通过索引下推减少回表，但这不等于它继续缩小了最初的索引扫描区间。

不要把它粗暴记成“范围后面的索引列完全失效”。应区分：

- 是否参与构造索引扫描边界。
- 是否能在索引记录上完成过滤。
- 是否需要回表后再过滤。

具体使用了哪些 key part，要以实际版本、数据和执行计划为准。

## 7. 如何设计联合索引

设计顺序可以压缩成四步：

```text
真实高频 SQL
-> where / join 中的查询入口
-> 范围、order by、group by
-> 是否值得增加覆盖列
```

### 7.1 先看真实 SQL

```sql
select id, amount
from orders
where user_id = ?
  and status = ?
  and created_at >= ?
order by created_at desc;
```

可以考虑：

```sql
create index idx_user_status_created_amount
on orders(user_id, status, created_at, amount);
```

原因：

- `user_id`、`status` 是等值条件，用于先缩小范围。
- `created_at` 是范围和排序字段，接在已固定的前缀之后。
- `amount` 作为返回列放在最后，用于形成覆盖索引。
- `id` 是主键，InnoDB 二级索引天然包含主键，一般不必重复加入。

### 7.2 等值在前、范围在后是常用起点

这不是脱离业务的绝对定律，但通常比把范围列放在最前面更容易连续使用多个 key part。

### 7.3 区分度不是唯一排序规则

“区分度高的列放最左边”只是考虑因素之一，不能覆盖真实查询模式。

如果高频查询是：

```sql
where user_id = ? and status = ?;
where user_id = ?;
```

`(user_id, status)` 能同时服务两条查询，通常比 `(status, user_id)` 更合适。

所以更准确的规则是：

> 让尽可能多的高频查询能够从联合索引最左侧连续使用。

### 7.4 排序字段接在固定前缀之后

```sql
where user_id = ?
  and status = ?
order by created_at desc;
```

索引 `(user_id, status, created_at)` 中，前两列被等值固定后，剩余记录按 `created_at` 有序，更有机会避免额外排序。

### 7.5 覆盖列最后考虑

覆盖索引能减少回表，但索引越宽：

- 占用空间越大。
- 单页能容纳的记录越少。
- 写入和更新维护成本越高。

所以先保证定位和排序能力，再判断高频查询是否值得追加少量返回列。

## 8. 索引不能有效定位的常见场景

“索引失效”是常见口语，更准确的判断可能是：

- 索引不能用于定位。
- 只能使用联合索引的一部分。
- 索引可以过滤，但不能缩小扫描区间。
- 索引可用，但优化器认为成本更高而不选择。

### 8.1 跳过联合索引最左列

```sql
-- 索引：(user_id, status)
where status = 'paid';
```

### 8.2 联合索引中间断开

```sql
-- 索引：(user_id, status, created_at)
where user_id = 10
  and created_at >= '2026-07-01';
```

### 8.3 范围条件后的列通常不能继续缩小完整扫描区间

```sql
-- 索引：(user_id, status, created_at)
where user_id = 10
  and status > 'paid'
  and created_at = '2026-07-01';
```

### 8.4 `like` 以通配符开头

```sql
where name like '%lin';
where name like '%lin%';
```

普通 B-tree 索引无法从字符串左侧确定扫描起点。固定前缀通常更容易形成范围：

```sql
where name like 'lin%';
```

### 8.5 对索引列做函数或表达式

不利于直接使用 `created_at` 原值的有序结构：

```sql
where date(created_at) = '2026-07-29';
```

更适合改写成原列范围：

```sql
where created_at >= '2026-07-29 00:00:00'
  and created_at < '2026-07-30 00:00:00';
```

### 8.6 隐式类型或字符集转换

如果 `phone` 是 `varchar`：

```sql
where phone = 13800138000;
```

更稳妥：

```sql
where phone = '13800138000';
```

连接列也应该尽量保持类型、长度和字符集一致，避免转换影响索引使用。

### 8.7 选择性低且返回大量整行

```sql
select *
from orders
where status = 'paid';
```

即使 `status` 有索引，如果 `paid` 占全表绝大多数，二级索引扫描加大量回表可能比全表扫描更贵。此时不是索引结构坏了，而是它没有明显减少成本。

## 9. 索引下推、回表过滤和覆盖索引不要混淆

假设索引是 `(user_id, status)`：

```sql
select *
from orders
where user_id > 100
  and status = 'paid';
```

可能出现三种不同工作：

1. `user_id` 用于确定索引扫描范围。
2. `status` 在二级索引记录上判断，提前丢掉不满足的记录。
3. 只有通过索引条件的记录才回表取得整行。

第 2 步属于索引下推的典型价值：减少完整行读取和回表。

执行计划中：

- `using index condition`：使用索引下推，仍可能需要回表。
- `using index`：查询被索引覆盖，通常无需读取完整数据行。

这两个含义不同。

## 10. 为什么有索引也不一定使用

索引只是优化器的候选路径。MySQL 使用基于成本的优化器，会根据统计信息估算：

- 表和索引大概有多少行。
- 索引值的分布和基数。
- 条件预计命中多少行。
- 要扫描多少索引记录。
- 是否需要回表，以及回表多少次。
- 是否需要额外排序或临时表。
- 是否可以通过覆盖索引直接返回。

选择性越高，通常越容易缩小范围：

```text
user_id：不同值很多，单个值通常命中少量行
status：不同值很少，单个值可能命中大量行
```

但不要死记某个“命中超过 20% 或 30% 就不走索引”的固定比例。是否选择索引取决于数据分布、返回列、页访问、缓存、统计信息和成本模型。

## 11. explain 和 explain analyze 的复习顺序

### 11.1 推荐观察顺序

```text
type
-> possible_keys
-> key / key_len
-> rows / filtered
-> extra
```

### 11.2 常见字段

#### `type`

常见访问方式：

- `const`：主键或唯一索引与常量等值比较，最多一行。
- `eq_ref`：连接中按主键或非空唯一索引匹配一行。
- `ref`：普通索引或唯一索引非完整前缀的等值访问。
- `range`：索引范围扫描。
- `index`：扫描整棵索引。
- `all`：全表扫描。

这个顺序只能用于建立直觉，不能脱离 `rows`、回表和实际耗时直接判定整条 SQL 的好坏。

#### `possible_keys`

优化器认为可能相关的候选索引。

#### `key`

优化器最终选择的索引。`key` 不为 `null` 只代表选择了索引，不代表扫描范围一定很小。

#### `key_len`

表示使用的索引键长度上限，可辅助判断联合索引使用了多长的前缀，但不要只靠它下结论。

#### `rows`

优化器估算要检查的行数，不是最终返回行数，也不一定等于真实扫描行数。

#### `filtered`

预计通过表条件过滤后保留的百分比。可以粗略估算：

```text
rows × filtered%
```

#### `extra`

重点关注：

- `using index`：覆盖索引。
- `using index condition`：索引条件下推。
- `using filesort`：需要额外排序过程。
- `using temporary`：使用临时表。
- `using where`：还需要按条件过滤。

### 11.3 explain 和 explain analyze

```sql
explain
select *
from orders
where user_id = 10;
```

`explain` 展示优化器计划和估算，不真正执行这条查询。

```sql
explain analyze
select *
from orders
where user_id = 10;
```

`explain analyze` 会真实执行语句，并给出：

- 估算成本和估算行数。
- 实际首行时间和总时间。
- 实际返回行数。
- 每个迭代器的循环次数。

因此在生产环境对慢 SQL 使用 `explain analyze` 前，必须先确认语句的执行成本和影响。

### 11.4 执行计划的核心判断

不要只问“走没走索引”，而要依次问：

1. 实际选择了哪个索引？
2. 用它构造了多窄的范围？
3. 预计和实际扫描多少行？
4. 是否发生大量回表？
5. 是否利用覆盖索引？
6. 是否需要额外排序或临时表？
7. 估算行数和实际行数是否差距很大？

## 12. 页结构如何影响索引性能

### 12.1 树高

```text
一次索引定位成本
≈ 从根到叶子的页面访问
+ 页内定位
```

索引键越短、内部目录项越小，一个页通常能保存越多导航项，扇出越大，树越有机会保持较低高度。

### 12.2 主键长度

InnoDB 每条二级索引记录都包含主键列：

```text
主键变长
-> 所有二级索引记录一起变大
-> 单页容纳记录减少
-> 索引页总量和缓存压力增加
```

所以短主键不仅优化主键索引，也降低所有二级索引的共同负担。

### 12.3 顺序主键与随机主键

单调递增主键通常让聚簇索引写入位置更集中，页面增长更稳定。

随机主键可能插入已有叶子页中间，更容易触及多个页面的剩余空间，并增加页面分裂和缓存局部性压力。

但不要绝对化：

- 自增主键不等于永远不分裂。
- UUID 也不是绝对不能作为主键。
- 选择要结合分布式生成、业务暴露、安全性和写入模式。

### 12.4 页分裂和合并

```text
目标页已满
-> 叶子页分裂
-> 父页新增目录项
-> 父页也满则继续向上分裂
-> 根页分裂时树高增加
```

删除后页面空间可以复用；满足条件时页面可能合并。但删除索引记录不等于表空间文件立即缩小。

## 13. 常见面试题与回答

下面的回答统一使用“结论 -> 原因 -> 边界”的结构。

### 13.1 什么是索引？

索引是存储引擎用于快速找到特定列值对应记录的数据结构。它通过提前维护有序结构，把全表扫描变成定位和小范围扫描。

索引能提高查询效率，但会占用空间，并增加增删改时的维护成本。

### 13.2 MySQL 索引有哪些分类？

分类角度不同，答案也不同：

- 按数据结构：B-tree、Hash、Full-text、Spatial 等。
- 按物理组织：InnoDB 聚簇索引、二级索引。
- 按约束特性：主键索引、唯一索引、普通索引。
- 按列数：单列索引、联合索引。

要补充存储引擎边界：InnoDB 普通用户索引主要是 B-tree；不能把 Memory 的 Hash 索引能力直接套到 InnoDB 普通索引上。

### 13.3 为什么 InnoDB 索引适合使用 B+ 树思想？

因为数据库按页读写，B+ 树的非叶子节点可以容纳大量导航项，扇出大、树通常较矮；数据集中在叶子层，查询路径稳定；叶子层有序连接，范围扫描只需定位起点后连续读取。

### 13.4 B 树和 B+ 树有什么区别？

B 树内部节点和叶子节点都可能保存数据；B+ 树内部节点主要导航，数据集中在叶子层。B+ 树内部页能容纳更多目录项，范围扫描也更直接，因此更适合数据库索引。

### 13.5 什么是聚簇索引？

聚簇索引是 InnoDB 用来组织和存储行数据的特殊索引。叶子记录保存整行数据。

有主键时使用主键；没有主键时选择合适的非空唯一索引；都没有时使用隐藏行 ID。

### 13.6 聚簇索引和主键索引完全等价吗？

在定义了主键的 InnoDB 表中，主键索引就是聚簇索引。

但“聚簇索引一定来自用户定义的主键”不正确，因为没有主键时 InnoDB 还会选择合适的唯一索引或生成隐藏聚簇索引。

### 13.7 什么是二级索引？

InnoDB 中除聚簇索引以外的索引都是二级索引。二级索引叶子记录包含二级索引列和对应主键列，需要其他字段时再通过主键查询聚簇索引。

### 13.8 什么是回表？

先从二级索引取得主键，再使用主键查询聚簇索引取得索引中不存在的列，这个过程叫回表。

回表不是一定慢，真正要看回表次数和访问页面的成本。

### 13.9 什么是覆盖索引？

如果一条查询需要的所有列都能从某个索引中取得，就不需要再读取完整行，这个索引对该查询形成覆盖索引。

覆盖索引是一种查询效果，不是一种独立索引类型。

### 13.10 为什么不建议滥用 `select *`？

它读取不必要的列，增大数据传输和内存开销；对二级索引查询还容易破坏覆盖效果，引入大量回表。

### 13.11 什么是联合索引和最左前缀？

联合索引是一棵按多个列依次排序的索引。索引 `(a, b, c)` 先按 `a` 排，`a` 相同再按 `b` 排，最后按 `c` 排。

最左前缀表示查询通常要从索引最左列开始连续匹配，才能形成可定位的有序区间。`where` 条件书写顺序不决定最左前缀，索引列顺序才决定。

### 13.12 范围查询之后的索引列还能用吗？

不能简单回答“完全不能”。

更准确地说：遇到范围条件后，后续列通常不能继续缩小整个索引扫描区间，但仍可能在索引扫描过程中参与过滤；使用索引下推时，还可能在回表前过滤掉部分记录。

最终应通过执行计划确认实际使用的 key part 和过滤位置。

### 13.13 什么是索引下推？

索引下推允许存储引擎先使用索引记录中已有的列判断部分 `where` 条件，只有满足条件的记录才读取完整行，从而减少回表和完整行读取。

`extra` 中的 `using index condition` 表示使用了这项优化。

### 13.14 哪些情况可能不能有效使用索引？

- 联合索引跳过最左列。
- 联合索引中间断开。
- 范围条件后续列不能继续缩小扫描区间。
- `like` 以通配符开头。
- 对索引列使用函数或表达式。
- 比较或连接列发生隐式类型、字符集转换。
- 条件命中大量记录，优化器认为全表扫描更便宜。

回答时最好说“不能有效定位、只能部分使用或成本不划算”，不要把所有情况都笼统说成索引彻底失效。

### 13.15 为什么有索引，MySQL 仍然可能全表扫描？

优化器按估算成本选择路径。如果条件命中全表大部分记录，并且查询需要整行，二级索引扫描加大量回表可能比顺序全表扫描更贵。

统计信息不准确也可能导致估算和实际情况偏离。

### 13.16 如何设计联合索引顺序？

先看高频 SQL，让常用等值查询入口位于左侧；再考虑范围、排序和分组字段；最后评估是否值得追加少量返回列形成覆盖索引。

不能只靠“区分度越高越靠前”这一条规则。

### 13.17 为什么主键通常建议短一些？

因为 InnoDB 二级索引记录包含主键。主键越长，每棵二级索引都越大，单页能保存的记录越少，磁盘空间和缓存压力越高。

### 13.18 为什么顺序主键通常更适合写入？

顺序值通常写入索引右侧附近，访问位置更集中，页面增长更稳定；随机值可能插入已有页中间，增加页面分裂和缓存局部性压力。

这是一种常见性能倾向，不是所有业务必须使用自增主键的绝对规则。

### 13.19 `explain` 重点看什么？

先看访问方式和实际索引，再看估算扫描行数和过滤比例，最后看是否覆盖、索引下推、额外排序或临时表。

关键不是只确认 `key` 有值，而是确认扫描范围、行数和回表成本是否合理。

### 13.20 `explain` 和 `explain analyze` 有什么区别？

`explain` 展示优化器的执行计划和估算；`explain analyze` 会真实执行查询，并显示实际时间、实际行数和循环次数，可用于比较估算与真实执行。

因为会执行，不能在生产环境对未知代价的语句随意使用。

### 13.21 前缀索引有什么作用和限制？

前缀索引只索引字符串前若干字符，可以减小索引记录和索引空间。

它会丢失完整列值，因此不能天然满足所有覆盖和排序需求；前缀长度还需要在空间和区分能力之间权衡。

### 13.22 什么时候适合建立索引？

- 高频用于 `where`、`join` 的列。
- 能明显缩小扫描范围的条件列。
- 有唯一性约束的业务列。
- 高频排序或分组，并且索引列顺序能够支持查询。
- 高频查询可以用较窄索引形成覆盖时。

### 13.23 什么时候不适合建立太多索引？

- 表非常小。
- 查询需要读取表中大部分记录。
- 列很少参与查询入口、排序或连接。
- 字段频繁更新，但索引带来的查询收益很小。
- 已有联合索引能够覆盖相同左前缀，继续增加重复索引收益有限。

## 14. 周日 SQL 自测

表结构：

```sql
create table orders (
    id bigint primary key,
    user_id bigint not null,
    status varchar(20) not null,
    created_at datetime not null,
    amount decimal(10, 2) not null,
    note varchar(500),
    index idx_user_status_created (user_id, status, created_at),
    index idx_status (status)
) engine = innodb;
```

先不看答案，判断每条 SQL：

1. 能从哪个索引的哪一列开始定位？
2. 能否形成连续扫描区间？
3. 是否需要回表？
4. 优化器是否一定选择该索引？

### 题目 1

```sql
select *
from orders
where id = 100;
```

### 题目 2

```sql
select id, user_id
from orders
where user_id = 10;
```

### 题目 3

```sql
select *
from orders
where user_id = 10
  and status = 'paid'
  and created_at >= '2026-07-01';
```

### 题目 4

```sql
select *
from orders
where status = 'paid';
```

### 题目 5

```sql
select *
from orders
where user_id = 10
  and created_at >= '2026-07-01';
```

### 题目 6

```sql
select *
from orders
where user_id > 10
  and status = 'paid';
```

### 题目 7

```sql
select *
from orders
where date(created_at) = '2026-07-29';
```

### 题目 8

```sql
select id, user_id, status, created_at
from orders
where user_id = 10
  and status = 'paid'
order by created_at desc;
```

### 自测答案

1. 使用聚簇索引按主键定位，叶子页有整行，不需要回表。
2. 可以使用 `idx_user_status_created` 的最左列 `user_id`；查询列都在二级索引记录中，不需要回表。
3. 可以连续使用 `user_id`、`status`，再按 `created_at` 做范围扫描；`select *` 通常需要回表。
4. `idx_status` 是候选索引，但如果 `paid` 命中大部分行且需要整行，优化器不一定选择它。
5. 可以用 `user_id` 定位；中间跳过 `status`，`created_at` 通常不能继续构造完整的连续范围；需要整行时回表。
6. `user_id` 用于范围扫描，`status` 通常不能继续缩小整个扫描区间，但可能通过索引下推参与回表前过滤。
7. 对 `created_at` 使用函数，不利于直接使用原列的有序值定位；应改写为一天的左闭右开范围，并考虑建立合适索引。
8. `(user_id, status, created_at)` 在前两列固定后可利用 `created_at` 顺序；二级索引包含查询所需列和主键，能够形成覆盖索引。

## 16. 最终速记卡

```text
1. 索引的价值：减少需要扫描的行和页。
2. B+ 树的价值：扇出大、树低、叶子有序、适合范围扫描。
3. InnoDB 的表数据：组织在聚簇索引中。
4. 二级索引叶子记录：二级索引列 + 主键列。
5. 回表：二级索引取得主键，再查聚簇索引。
6. 覆盖索引：查询所需列都能从索引取得。
7. 联合索引：按列顺序依次排序，不是多棵单列索引。
8. 最左前缀：从最左边形成连续可定位区间。
9. 范围之后：后续列通常不能继续缩小整个扫描区间，但仍可能参与索引过滤。
10. 索引设计：查询入口 -> 范围和排序 -> 必要的覆盖列。
11. 有索引不一定走：优化器选择估算成本更低的路径。
12. explain 不只看 key：还看扫描范围、rows、filtered、回表、排序和临时表。
13. using index：覆盖索引；using index condition：索引下推。
14. 主键尽量短：它会被带入所有二级索引。
15. 最终原则：规则用于分析，执行计划用于验证。
```
